# Release packaging and deployment alignment

Scope is recorded in `development/planning/release-0.11.0-alpha.1.md`.
Observed on 2026-10-17; this report does not assert remote publication or deployment.

## Changes

- Root Gradle version is the single canonical `0.11.0-alpha.1` SemVer. Subprojects
  inherit it, so Maven, JARs, tarballs and npm manifests agree without a leading
  `v`. `printReleaseVersion` exposes the same value to automation.
- CLI common source is generated by `generateCliVersion`; JVM and Node display
  `Branchline CLI v0.11.0-alpha.1`. `CliVersion.CURRENT` no longer has a separately
  maintained release literal. Generated source has a version input and output
  directory. Node package assembly declares compiled-code/template/version inputs
  and the assembled directory output.
- `CliVersionTest` compares the generated constant, packaged npm version and
  actual packaged Node `--version` output to the canonical value supplied by
  Gradle. It requires Node, as the packaging gate does.
- Release checkout uses the release tag, explicit dispatch tag, or dispatch/push
  source SHA. An explicit dispatch tag must already exist. With an empty dispatch
  tag, a full release derives `v<canonical-version>`; benchmark-only runs retain
  snapshot/perf naming. Existing tags must resolve to the checked-out commit.
- Full-release tags must equal `v<canonical-version>`. Exact artifact filenames
  replace first-glob selection. Both packaged JVM and Node version commands and
  the npm manifest must agree before any release creation or upload.
- Full releases include SHA256SUMS and release-metadata.json with source SHA,
  canonical version and release tag. Asset names retain the customary tag `v`.
- Release creation occurs after successful builds/capture/version checks, as a
  draft. New/completed drafts publish only after all uploads succeed. Alpha and
  performance releases are prereleases, with `--latest=false`; existing release
  prerelease status must agree. A fresh remote-tag check rejects a tag that moved
  to another commit. An existing draft without a tag must already target the
  exact built SHA. Repository-wide release workflow concurrency serializes all release artifact
  mutations, including empty-tag and explicit-tag dispatches for the same version.
- Existing `+performance`, `+jsonata`, manual JMH/JSONata controls and report
  generation are preserved. Full release itself enables Pages, including when
  `run_jmh=false` and `run_jsonata=false`.
- Reusable Pages receives the actual built commit SHA and canonical version.
  Checkout SHA/version are checked again. The generated public `/build-info/`
  page and `/release-metadata.json` expose that checkout and workflow run.
- Pages still builds **MkDocs into `site/`**. `./gradlew docsBuild` instead builds
  Diplodoc into `docs-compiled/`; it alone does not validate the deployed site.

## Remaining parent gates and risks

No Gradle task was run by the packaging agent, to avoid competing Gradle jobs.
The parent owns serialized execution and should record these real results:

```bash
./gradlew :cli:jvmTest --tests '*CliVersionTest' :cli:blShadowJar :cli:packageJsCli :interpreter:jvmJar :vm:jvmJar :interpreter:packageInterpreterJs
./gradlew :cli:jvmTest :cli:jsNodeTest
./gradlew docsBuild
mkdocs build --site-dir site
```

The final release workflow must succeed for the exact tagged SHA, followed by
public metadata and playground browser acceptance. The shell harness does not
execute GitHub Actions expressions, credentials, archive creation, gh mutations,
MkDocs, or Pages. A failed upload can leave an unpublished draft and a rerun is
needed. Existing published releases can still be updated when explicitly rerun;
GitHub repository immutability settings may reject those updates. Metadata proves
the deployed source commit; it does not claim artifact/site byte reproducibility.

The packaging/version/deployment changes trigger a service-contour update. The
parent owns INDEX, VERIFY, SERVICE_MAP and unresolved-gap reconciliation; this
agent did not edit shared contour files or product documentation.

## Follow-up from the parent's first full build

The parent reported a real Gradle producer-validation failure: interpreter JS
packaging consumed a distribution directory also written by the browser task,
but depended only on the Node task. Both Kotlin 2.3 distribution tasks originally
shared `build/dist/js/productionLibrary`. Inspection of the installed Kotlin
Gradle plugin with `javap` confirmed the library distribution producer is a
Gradle `Copy` task.

`interpreter/build.gradle` now gives the Node distribution its own
`build/dist/js/nodeProductionLibrary` destination. The archive takes its source
from the Node task provider itself and keeps its explicit dependency. The browser
path stays `build/dist/js/productionLibrary`, which is the exact path imported
by `playground/src/worker.ts` and read by its dependency check. The two producers
therefore cannot overwrite one another when packaging and docs run together.

The parent's full build also showed `playgroundBuildAssets UP-TO-DATE` despite
rebuilt runtime JavaScript. Its declared inputs now cover the browser runtime
directory, source, example catalog, build/test scripts, public assets, package
and lock/config JSON, root HTML and Vite configuration. Its sole output remains
`docs/assets`, matching `playground/vite.config.ts`; no new output directory
ownership overlaps were introduced. The Node producer change leaves runtime
imports and deployment's unconditional `npm run build` path intact.

Only source/plugin inspection and `git diff --check` were run for these two
repairs. The parent must rerun `:interpreter:packageInterpreterJs docsBuild`
together in the serialized real gate, inspect the archive's package.json and
modules, and verify the playground task reruns after runtime/example/config input
changes. The packaging agent did not run Gradle or claim those results.
